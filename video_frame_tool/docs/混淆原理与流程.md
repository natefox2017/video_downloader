## 一、一句话原理

**先把容器写坏，让本地拒读；平台服务端容错高，照样能解出码流。**

- 本地播放器按规范严格解复用 → 读到被抹坏的字段 → 整个文件拒收（`Invalid data found`）；
- 平台上传后会**先重做一遍转码/转封装**，解复用容错度高，直接读码流里 SPS 的真实尺寸 → 正常出片。

画面数据本身是好的：把容器修好（补回分辨率字段）就能无损还原播放 ——
备份目录里的 `容器还原_deobf.py` 就是干这个的（用法见该目录 README）。

## 二、容器的五处人为破坏

对样本的逆向结论（`_clone_container` 逐项复刻）：

| 位置 | 破坏方式 | 后果 |
|---|---|---|
| `Video` 的 `PixelWidth`/`PixelHeight` | 替换成同长度 `Void` | **致命**：解码器读不到分辨率，整个文件被判无效 |
| `Info` | 删 `TimestampScale`；`MuxingApp`/`WritingApp` 的元素 ID 写错 +1（0x4D81/0x5742） | 结构指纹异常 |
| `SeekHead` | 首子元素 Void 顶掉 CRC；某条 SeekID 写成 `0x84ECECEC` | 索引失效 |
| `Cues` | 索引全部失效 | 无法 seek（不影响顺序播放） |
| `Tags` | `DURATION` 写死成样本值 `00:00:01.121` | 元数据不可信 |

**Void 与原字段等长**是关键设计：文件结构不位移，后面所有元素偏移原样保留。
最小修复 = 只把 12 字节的 `Void+Void+DisplayUnit` 换回 `PixelWidth+PixelHeight`。

容器改写是**纯 Python 逐字节重建**（`_parse` / `_serialize` / `_write_size`），不重编码：
CRC-32 按 ffmpeg 约定以小端落盘（`struct.pack("<I", zlib.crc32(body))`）、Segment size 固定 8 字节编码、
Cues 的 `CueClusterPosition` 随头部长度整体平移。

## 三、编码配方（从样本码流反推，参数级 1:1）

x264 会把**本次编码的完整参数表**写进第一帧的 SEI（user_data_unregistered），
dump 出来即得到对方"命令行"：

```
ref=3 deblock=1:1:0 analyse=0x3:0x113 me=hex subme=7 psy_rd=1.00,0.00 mixed_ref=0
me_range=16 trellis=0 8x8dct=1 chroma_qp_offset=-4 threads=4 lookahead_threads=4
sliced_threads=1 slices=4 interlaced=tff bframes=3 b_pyramid=2 weightb=1 open_gop=0
weightp=0 keyint=250 keyint_min=25 scenecut=40 rc_lookahead=10 rc=crf mbtree=1
crf=22.0 qcomp=0.60 aq=1:1.00
```

要点：**4 切片/帧 + 隔行编码** + 每帧 1 个小 SEI + AAC-LC 44.1kHz 立体声 192kbps。
输出强制 **720×1276 / 30fps / High L3.1**（对齐样本，不按源视频）。

ffmpeg 侧的等价写法（`CLONE_X264`，5 个易踩的坑）：

| 目标参数 | ffmpeg 写法 | 原因 |
|---|---|---|
| `deblock=1:1:0` | `deblock=1\:0\:0` | ffmpeg 用 `:` 分隔 -x264-params，必须转义 |
| `analyse=0x3:0x113` | `partitions=i4x4,i8x8,p8x8,b8x8` | `analyse=all` 会多开 p4x4 |
| `chroma_qp_offset=-4` | `chroma-qp-offset=-2` | x264 在 subme≥7 时自动再减 2 |
| `mbtree=1` | 显式写 | `preset superfast` 自带 `--no-mbtree` |
| `interlaced=tff` | `-flags +ilme+ildct -top 1` 且放在 `-x264-params` 之前 | 顺序不对不生效 |

已知不可复现项：逐帧 SEI 的载荷字节（样本 0x42/0x32 两种，本实现全 0x32），
属 x264 core 164 vs 165 的 `pic_struct` 取值差异，参数表既然零差异就无需纠结。

## 四、画面层：上下场混合（fieldmix 的核心）

样本 22.mp4 的画面是把素材**按场拆开、一场换成一整张静态彩色色块图**（逐场量化结论）：

| 场 | 内容 | 实测证据 |
|---|---|---|
| 偶行场 | 一整张静态强彩色色块图，**全程不变** | 均值恒定 163.5、标准差 16.5，跨 920 帧 MAD ≤ 0.49 |
| 奇行场 | 真实画面 = 原片对应帧 | 与原片同场 MAD ≈ 10（重编码噪声级） |
| 帧对齐 | 样本[i] ↔ 原片[i]，无时移 | 逐帧扫描确认；样本丢掉了最后一帧（930 vs 931） |

实现要点（`_encode_cmd_fieldmix`）：

- 色块图用 `nullsrc + geq` 生成 **1 帧**再 `loop=-1` 复用 —— 逐帧重算会闪烁且码率暴涨；
  种子取 `time.time_ns()`，**每个成品图案都不同**。
- 混合用 `blend=all_expr='if(eq(mod(Y,2),0),if(lt(N,1.5),A,B),A)'`。
  ⚠️ `blend` 的 `N` **从 1 起算**，所以判断「第 0 帧」必须写 `lt(N,1.5)`；写 `lt(N,1)` 永远不生效。
- **第 0 帧整帧保留原画** —— 平台用第一帧取封面，第 0 帧若是色块，成品封面就是彩虹横纹。
- 转 `yuv420p` 时必须 `interl=1` 按场采样色度，否则强彩色上场会污染原画下场。
- 画面帧标记写 **BFF**（`-top 0`），容器 `FieldOrder` 仍伪装成 **TFF**；两者相反是样本的关键特征。
- 按「源帧数 − 1」截帧（`needs_frames=True`），复刻样本丢掉最后一帧的行为。

## 五、裂变随机化（每条成品字节必不同）

两个独立随机源，编码参数本身**不随机**（不抖 CRF、不写假值——那是被查重的根因）：

1. 色块图种子取 `time.time_ns()`，每条成品图案不同；
2. 容器 `DateUTC` 取该条的处理时刻（`_now_date_ns`，macOS 2001 基准）。

叠加「前贴/尾贴每条独立随机抽取」，N 条产物哈希必不同。

## 六、处理流程

```
封面图（随机 1 张）  ┐
前贴（随机 N 个）    ├─ fission.concat_segments：各段统一重编码成 720×1276/30fps
搬运（按序取 1 个）  │   → concat demuxer -c copy 无损拼接（无音轨的段补静音轨）
尾贴（随机 N 个）    ┘   封面 = 强制拉伸后叠在第一段的第 0 帧（时长/帧数不变）
        ↓ 拼成标准 MP4 中间件（只有搬运、无任何拼接项时跳过这步，直接进混淆）
obfuscate.process_video：一次 x264 重编码（配方见第三节）→ mid.mkv
        → 自写 EBML 容器改写（_clone_container，含容器破坏 + 元数据）
        → 输出 <搬运名>_NN.mp4（本地拒读、平台可播）
```

顺序固定 **拼接 → 混淆**；拼接只负责产出一条标准 MP4，混淆只吃「已拼好的视频」这一个输入，
两者完全解耦。

## 七、多算法扩展

`obfuscate.py` 第四节是**算法注册表**，把「混淆算法」抽象成可切换的对象。
**当前只有 `fieldmix` 一个。**

**统一接口**：

| 字段 | 类型 | 职责 |
|---|---|---|
| `name` | 字符串 | 算法唯一标识 |
| `label` | 字符串 | 展示名 |
| `encode_cmd(ffmpeg, src, mid, frames=None) -> list` | 重编码命令 | 先把源视频压成标准 MKV 中间件 `mid` |
| `rewrite(mid_bytes) -> bytes` | 容器改写 | 把中间件改成该算法的混淆容器 |
| `needs_frames` | 布尔 | 为真时调用方按「源帧数 − 1」截帧 |

**加新算法的步骤**：

1. 在 `obfuscate.py` 写一个 `_algo_xxx()` 返回上面字段的 dict；可复用已有的
   `_parse`/`_serialize`/`_find`/`_crc_node` 等 EBML 基础工具。
2. 在 `ALGORITHMS = {a["name"]: a for a in [ ... ]}` 里注册一行。
3. `process_video(..., algorithm="xxx")` 即可切换；`get_algorithm(name)` 按名取、未知名回落默认。

**命名约定（用户定，务必遵守）**：算法名 = 6 位日期 `YYMMDD`（如 `260919`），
对应「该算法通过查重实测的当天」；**每天只留一个最终版**，同一天测了多套只保留最终确认的那个。

**调用链**：`window.py`（界面）→ `fission.process_one_output(..., algorithm=...)` →
`obfuscate.process_video(..., algorithm=...)`。`algorithm` 参数全程透传。

## 八、与平台的关系（重要，决定这招有没有用）

实测（样本 11 → 22 → 33，33 是快手对 22 的转码产物）：

- **平台不丢帧**：22 与 33 都是 930 帧，平台一帧没丢；丢 1 帧的是 22（同行软件）。
- **平台会把色块层抹掉**：22 的偶行场恒定 163.5/16.5，33 的偶行场变成 106.3/59.6 ——
  去隔行算法把「牺牲场」扔了，画面回到接近原片的状态。
- **结论**：色块层只在**上传瞬间**骗过系统，一进转码管线就被撸掉；
  平台判重最终看的是**色块底下那层原画面**。

推论（指导选素材）：**原画面已经被上传过的素材，怎么处理都会撞库**；
必须用从未上传过的干净素材，色块层才真正起到「上传时错开」的作用。

## 九、风险与注意

1. **重编码 ≠ 过内容查重**：换容器/切场只改文件哈希与编码指纹，
   平台若做画面级内容比对，仍可能命中（见第八节）。
2. 混淆后的文件**本地无法预览/剪辑**，封面与时长元数据不可信；要检查画面先用工具还原容器。
3. 不同平台容错度不同，抹坏关键字段有转码失败的风险；重要素材先留一份标准 MP4 底稿。
