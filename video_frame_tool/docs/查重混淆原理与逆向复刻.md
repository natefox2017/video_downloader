# 查重混淆原理与逆向复刻方法论

> **⚠️ 2026-09-19 更新**：本文第「一」节的结论里写的「画面内容不动、不叠加任何噪点/色块/调制」
> 是拿 `1.mp4 / 2.mp4 / 3.mp4` 三个**已被替换掉的旧样本**得出的，**已被推翻**。
> 用用户后来提供的真样本 `11 / 22 / 33.mp4` 逐场量化后确认：同行软件的产物 `22.mp4`
> **画面确实做了一层处理 —— 上下场混合**（偶行场铺静态强彩色色块图、奇行场放原画面；
> 第 0 帧整帧保留原画）。而且平台（快手）转码时**会把这层色块丢掉、还原成接近原片的画面**，
> 所以判重最终看的还是色块底下那层原画面。
> 完整结论与数据见 [`../../复刻22_已验证备份_20260919/README.md`](../../复刻22_已验证备份_20260919/README.md)。
> 本文关于「如何用两个样本逆向复刻配方」的**方法论部分仍然可用**。

> 本文档回答两个问题：
> 1. 为什么「容器混淆 + 重编码」这套方案能过快手查重？
> 2. 快手查重算法更新后，如何用「原视频 + 快手处理后的视频」两个样本，快速逆向并复刻出新的过查重配方？

---

## 一、结论先行（TL;DR）

过查重的本质是 **「画面内容不变 + 编码指纹破坏 + 逼迫平台重转码」**，**不是**「把画面改得不一样」。

| 维度 | 是否要动 | 说明 |
|---|---|---|
| 画面内容 | **不动** | 只做分辨率/帧率缩放，不叠加任何噪点/色块/调制 |
| 编码指纹（GOP/量化/SEI/码流） | **破坏** | 重编码一次即天然改变 |
| 容器 | **混淆** | 抹掉分辨率元数据 → 本地拒读 → 逼平台走「重转码」而非「直传」 |

## 二、实测数据（样本：1=原片 / 2=软件产物 / 3=快手产物）

### 2.1 三者规格对比

| | 1 原视频 | 2 软件处理后 | 3 快手处理后 |
|---|---|---|---|
| 分辨率 | 1080×1920 | 720×1276 | 716×1276 |
| 帧率 | 60fps | 30fps | 30fps |
| 容器 | 标准 MP4 | MKV（拒读） | 标准 MP4 |
| 编码 | h264 | x264 core165 逐帧SEI | h264 High L31 |
| 码率 | 11.6 Mbps | 2.66 Mbps | 2.14 Mbps |
| 大小 | 45 MB | 10.6 MB | 8.2 MB |

### 2.2 画面对比（按时间戳对齐，逐帧 PSNR/MAD）

| 对比 | MAD | PSNR | 结论 |
|---|---|---|---|
| 1 vs 2（原片 vs 软件） | 1.2~2.8 | 36~42 dB | 画面几乎没变，只缩放+重编码 |
| 2 vs 3（软件 vs 快手） | 6~9 | 21~25 dB | 快手重转码，量化噪声 |
| 1 vs 3（原片 vs 快手） | 6~10 | 21~25 dB | 差异主要来自快手自己的重编码 |

### 2.3 快手做了什么处理（从 2→3 逆推）

- 分辨率 720→716（**左侧裁 2 像素**，不是居中裁）
- 码率 2.66→2.14 Mbps（重新量化压缩）
- 容器 MKV→标准 MP4（完整重封装）
- 结论：**快手对上传视频做了一次「完整解码 → 重编码 → 重封装」**

## 三、核心原理（为什么能过查重）

### 3.1 平台的查重是「双重指纹」

平台判定「重复视频」通常比对两种指纹：

1. **内容感知哈希**（pHash / 视频级 aHash / 关键帧 pHash）—— 比对的是「画面长什么样」。这层**对内容敏感，对编码参数不敏感**。
2. **编码/文件指纹**（文件 MD5、码流结构、GOP 边界、量化参数序列、SEI 时序、关键帧分布）—— 比对的是「这个文件是怎么编码的」。这层**对重编码敏感**。

### 3.2 为什么「画面不动」反而能过

- 我们的视频是**用户自己要发的新内容**，不是盗用他人视频，所以「内容指纹」本来就不会撞库。
- 真正会触发「重复/搬运」判定的，是**同一条视频被重复上传**时的「编码指纹」相同（比如同一台手机录的原片反复传）。
- 所以只要**破坏编码指纹**，让平台认为「这是一个全新的编码产物」，就能过。

### 3.3 容器混淆的作用 = 保险丝

- 正常可读的 MP4，快手可能走「直传 / 轻转码」路径，**保留原始编码指纹**。
- 抹掉分辨率元数据后，本地播放器/快手的标准解析器**拒读**，快手只能走「**完整解码 → 重转码 → 重封装**」路径。
- 这一步重转码天然把 GOP 结构、量化参数、SEI 时序全部打乱 → 编码指纹被彻底破坏。

### 3.4 完整链路

```
原视频
  ↓ 软件处理（只改编码，不改画面）
重编码：scale=720x1276, fps=30 + 隔行标记 + x264 固定配方(CRF22)
  ↓
容器混淆：抹分辨率元数据 → 本地拒读
  ↓ 上传快手
快手完整解码 → 重转码（左裁2px、降码率）→ 重封装成标准MP4
  ↓
成品：画面内容与原片一致，但编码指纹已面目全非 → 过查重
```

## 四、当前生效配方（已固化进代码）

见 `src/obfuscate.py`，关键参数**写死不动**：

```
分辨率 / 帧率：720 × 1276 / 30fps（对齐样本 22.mp4）
编码器：libx264, preset superfast, CRF 22（固定，不抖动）
隔行标记：-flags +ilme+ildct -top 1（必须在 -x264-params 之前）
x264 配方 CLONE_X264（37 项，逐字对齐样本 SEI）：
  ref=3, deblock=1:0:0, partitions=i4x4,i8x8,p8x8,b8x8, me=hex, subme=7,
  psy-rd=1.00,0.00, mixed-refs=0, me-range=16, trellis=0, chroma-qp-offset=-2,
  threads=4, lookahead-threads=4, sliced-threads=1, slices=4, bframes=3,
  b-pyramid=2, b-adapt=1, b-bias=0, direct=1, weightb=1, open-gop=0,
  weightp=0, keyint=250, keyint-min=25, scenecut=40, intra-refresh=0,
  rc-lookahead=10, qcomp=0.60, aq-mode=1, aq-strength=1.0, mbtree=1
音频：aac 192k 44100 2ch
元数据：Duration = 真实时长，DateUTC = 当前时间，Tags DURATION = 真实时长格式化
容器：MKV，抹掉 PixelWidth/PixelHeight（两个 Void + 0x54B2 顶掉），SeekHead/Cues 索引按样本形状改写
```

**雷区（改代码前必看，都在注释里）**：
- `deblock=1\:0\:0` 的反斜杠转义不能丢（ffmpeg 用 `:` 分隔 -x264-params）。
- 隔行标记必须放在 `-x264-params` **之前**，否则 x264 不认。
- CRF 不要随机抖动（曾试过 ±1，导致产物和样本对不上，已回退固定 22）。
- 元数据**不要写死假值**（曾写死 1.032s，与真实时长矛盾，可能被当异常信号，已回退真实时长）。

## 五、快手算法更新后的逆向复刻流程（本文档的核心目的）

> 触发条件：快手更新了查重/转码算法，旧的混淆产物又过不了查重了。
> 你需要提供的样本：**① 原视频 + ② 快手处理后的视频**（各一个，最好同一素材）。

### 5.1 第一步：定位「快手这次改了什么」

拿到两个样本后，按下面的清单逐项比对，找出差异点：

```
1. 容器层
   - ffprobe 看 format_name / 扩展名是否一致
   - mkvforge.py inspect 看是否有「异常元素 / 索引失效 / 分辨率缺失」等破坏痕迹

2. 编码层（关键）
   - 分辨率 / 帧率：width/height/avg_frame_rate
   - 编码器：x264 core 版本、profile、level
   - 码率：bit_rate（快手转码会用新码率档）
   - GOP：关键帧间隔 keyint、关键帧数量
   - SEI：是否每帧插 SEI、SEI 载荷内容

3. 画面层（最重要，逐帧对齐比对）
   - 用时间戳对齐抽帧，算 PSNR / MAD
   - 看快手有没有做：裁边(单边/居中/几像素)、缩放、亮度/对比度/饱和度调整、加噪、
     隔行/去隔行、旋转/镜像、加黑边/白边、加 logo/时间戳
   - 用「穷举平移搜索」找裁边量（dx/dy 扫描，MAD 最小的即真实偏移）

4. 元数据层
   - Duration / Tags DURATION / DateUTC 是否写死还是真实值
```

### 5.2 第二步：逆推「新算法」的变换链

把 ①→② 的变化抽象成一条「滤镜链」。例如本次实测逆推出的链是：

```
原视频(1080x1920@60)
  → scale 到 720x1276
  → 降帧率到 30
  → x264 重编码（固定配方 + 隔行标记）
  → MKV 容器混淆（抹分辨率）
  → [快手] 左裁 2px → 716x1276 + 降码率 + 重封装
```

快手更新后，② 可能变成：不同裁边量、不同输出分辨率、不同码率、不同色度处理等。
**把 ② 的每一项变化都量化出来**（裁几像素、码率多少、PSNR 多少）。

### 5.3 第三步：反向生成「能过新算法的产物」

关键原则：**软件产物要尽可能「逼近快手会重新转码成什么样」，但比快手多一步「容器混淆逼它重转码」**。

具体做法：
1. 保持「画面内容不变」—— 只做分辨率和帧率的缩放，**不要**加噪点/色块/调制。
2. 编码参数对齐新样本 ② 的编码特征（分辨率、帧率、profile、level、码率档位）。
3. 容器混淆照旧（抹分辨率 → 拒读 → 逼平台重转码）。
4. 用「5.1 的清单」验证软件产物和 ② 的画面对齐度（PSNR 应 >35dB，即画面内容一致）。

### 5.4 验证闭环

生成 N 份（改分辨率/码率/GOP 各一档）发快手实测，确认能过查重后，把生效参数固化进 `obfuscate.py`，并更新本文档第四节的配方。

## 六、可复用的逆向工具链（本机已验证）

| 工具 | 用途 |
|---|---|
| `ffprobe -show_entries stream/format` | 读分辨率/帧率/码率/编码器 |
| `video_shield/mkvforge.py inspect` | 分析容器破坏痕迹、SEI、编码指纹 |
| `video_shield/mkvforge.py repair` | 把混淆产物还原成可解码 MP4（对比画面用） |
| `video_shield/mkvforge.py clone` | 按配方 1:1 复刻混淆产物 |
| `ffmpeg -ss <t> -frames:v 1` | 按时间戳抽帧（**必须时间对齐，不能按帧号**） |
| Python + Pillow + numpy | 逐帧 PSNR/MAD 对比、穷举平移找裁边量 |

**关键手法备忘**：
- 帧对比**必须按时间戳对齐**（`-ss` 抽帧），不能按帧号（60fps vs 30fps 帧号不对应同一时刻）。
- 找裁边量：对 dx∈[-4,4] 穷举平移，MAD 最小的 dx 即真实偏移。
- 判断「画面内容是否被动」：软件产物 vs 原片的 PSNR 应 >35dB（内容没动）；若 <30dB 说明画面被实质改变（方向错了）。

## 七、历史踩坑记录（避免重蹈覆辙）

1. **画面层加奇偶行调制 / 噪点 / 色块 → 反而过不了**。错在「改了画面内容」，可能触发内容级查重。正确方向是「画面不动，只破坏编码指纹」。
2. **CRF 随机抖动 ±1 → 产物和样本对不上**。回退固定 CRF 22。
3. **元数据写死假值（1.032s）→ 与真实时长矛盾**，可能被当异常信号。回退真实时长+当前时间。
4. **geq 滤镜乘法调制会 wrap 成白色**（TV 域 <16 写回 uint8 溢出）。已弃用该方案。
