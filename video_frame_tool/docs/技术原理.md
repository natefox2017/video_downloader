# 视频混淆：技术原理与实现

**本项目唯一的原理文档。** 只描述当前生效的实现，不含历史方案。
代码约束与易踩坑点写在项目根 [`AGENTS.md`](../../AGENTS.md)，两处不重复。

对应模块：

| 模块 | 职责 |
|---|---|
| `src/fission.py` | 组段（封面 + 前贴 + 搬运 + 尾贴）→ 拼接成一条标准 MP4 |
| `src/obfuscate.py` | fieldmix 画面处理 + x264 重编码 + 容器改写（核心） |
| `src/ui/window.py` | 界面与并发调度，把上面两步串成一条成品的产出流程 |

---

## 一、要解决的问题

一条素材要在平台上多发几次，但平台会查重：同一条视频反复上传、或画面与库里已有内容高度相似，
就会被判重、限流。本项目把**一条搬运素材**裂变成 N 条互不相同的成品。

理解本方案的前提是先分清平台的两层指纹：

| 指纹层 | 比对什么 | 对什么敏感 | 本方案的处理 |
|---|---|---|---|
| 编码 / 文件指纹 | 文件字节、码流结构、GOP 边界、量化参数序列、SEI 时序 | 重编码 | 一次 x264 重编码 + 容器改写，彻底打乱 |
| 内容 / 画面指纹 | 画面长什么样（感知哈希、关键帧比对） | 画面内容本身 | 上下场混合（fieldmix），**只在上传那一刻改变系统看到的画面** |

---

## 二、一句话原理

**先把文件容器写坏，让本地播放器拒读；平台服务端容错度高，照样能解出码流，于是被迫重走一遍
「完整解码 → 重转码 → 重封装」，原始编码指纹在这一步被彻底打乱。同时在画面上做上下场混合，
在上传瞬间改变系统看到的画面。**

- 本地播放器按规范严格解复用 → 读到被抹坏的字段 → 整个文件拒收（`Invalid data found`）；
- 平台上传后先做一遍转码/转封装 → 解复用容错度高 → 直接读码流里 SPS 的真实尺寸 → 正常出片。

画面数据本身是完好的：把容器补回来就能无损播放（还原方法见第十一节）。

### 必须记住的一条实测结论

平台转码会**把色块场整层丢掉**，判重最终比对的是**色块底下那层原画面**（数据见第十节）。
所以：**原画面已经上传过的素材，怎么处理都会撞库。**色块层只在「上传瞬间」错开，不是护身符。
选素材的硬规则 —— 只用从未上传过的干净素材。

## 三、产物形态

| 属性 | 值 | 说明 |
|---|---|---|
| 显示分辨率 | 720 × 1276 | 编码时写 720×1280 真隔行，x264 为满足「隔行高度必须是 32 的倍数」自动 crop 掉 1 行 |
| 帧率 | 30 fps | 不随源片变化 |
| 编码 | H.264 High L3.1 / max_ref=4 / `frame_mbs_only=0`（真隔行） | 与参考样本逐项一致 |
| 音频 | AAC-LC 44.1kHz 立体声 192kbps | 不动音轨内容 |
| 本地 ffprobe | `Invalid data found when processing input` | 预期行为，不是 bug |
| 平台 | 可正常播放 | 服务端重转码 |
| 单条之间的关系 | 字节级互不相同（md5 必不同） | 见第九节 |

命名：`<搬运视频名>_<两位序号>.mp4`（序号 01~99，全局递增），输出目录默认 `~/Desktop/out`。

## 四、完整流水线

```
封面图（随机 1 张）  ┐
前贴（随机 N 个）    ├─ fission.concat_segments
搬运（随机抽 1 个）  │    每段先各自重编码成 720×1276 / 30fps（缩放补黑边 + 补齐音轨）
尾贴（随机 N 个）    ┘    → concat demuxer `-c copy` 无损拼接
                          封面 = 强制拉伸铺满后 overlay 到第一段的第 0 帧（时长/帧数不变）
        │
        ▼  joined.mp4（只有搬运、没开任何拼接项时跳过这一步，直接把搬运喂给混淆）
        │
obfuscate.process_video
        ├─ (a) 一次 x264 重编码（配方见第六节）→ 中间件 mid.mkv
        └─ (b) 纯 Python EBML 容器改写（见第七节）→ NN_<搬运名>.mp4（如 01_x31.mp4）
```

顺序固定：**拼接 → 混淆**。两者完全解耦：拼接只负责产出一条标准 MP4，
混淆只吃「一条已拼好的视频」这一个输入，不关心它是怎么来的。

拼接这一步的三个要点：

1. 各段规格先统一，否则 concat demuxer 拼不起来；统一规格 = 成品规格（720×1276 / 30fps）。
2. 无音轨的段用 `anullsrc` 补一条静音轨，保证所有段的流结构一致。
3. 封面不额外插帧：`overlay=enable='eq(n,0)'` 只换第 0 帧的画面，时长与帧数一点不变。

## 五、画面层：fieldmix（复刻参考样本 22.mp4）

参考样本 `22.mp4` 是某去重软件对 `11.mp4` 的处理产物，传到快手后能规避查重。
逐场量化后，它的画面结构是**上下场混合**：

| 场 | 内容 | 实测证据 |
|---|---|---|
| 偶行场 | 一整张**静态强彩色色块图**，全程不变 | 均值恒定 163.5、标准差 16.5，跨 920 帧 MAD ≤ 0.49 |
| 奇行场 | **真实画面** = 原片对应帧 | 与原片同场 MAD ≈ 10（重编码噪声级） |
| 帧对齐 | 样本[i] ↔ 原片[i]，**无时移** | 逐帧扫描确认 |

实现（`_encode_cmd_fieldmix` + `_fieldmix_pattern`）：

- 色块图用 `nullsrc + geq` 生成**只出 1 帧**再 `loop=-1` 复用 —— 逐帧重算会闪烁且码率暴涨。
  种子取 `time.time_ns()`，**每个成品的图案都不同**。
- 色块图**自带 alpha 行遮罩**（偶行 255 = 不透明、奇行 0 = 透明），合成用：

  ```
  [src][pat]overlay=format=yuv444:enable='gte(n,1)':shortest=1
  ```

  - `enable` 用**从 0 起算**的 `n`（与 `blend` 的 `N` 从 1 起算不同），`gte(n,1)` 即「第 0 帧不动」。
  - `format=yuv444` 必须显式写：默认 `auto` 走 RGB 混合，YUV↔RGB 往返会带来 ±1 级误差。
  - 行奇偶判断退化成**一次性的 1 帧遮罩生成**，合成时只做 SIMD 覆盖。
- **第 0 帧整帧保留原画（不叠色块）** —— 平台用第一帧取封面，第 0 帧若是色块，成品封面就是彩虹横纹。
- 转 `yuv420p` 时必须 `scale=...:interl=1` 按场分别采样色度，否则强彩色上场会污染原画下场。
- 画面帧标记写 **BFF**（`setfield=bff` + `-top 0`），而容器的 `FieldOrder` 仍伪装成 **TFF**；
  这个自相矛盾是样本的关键特征，别「修正」掉。
- 按「源帧数 − 1」截帧（算法对象的 `needs_frames=True`），复刻样本丢掉最后一帧的行为。

#### 2026-09-19 提速：blend → alpha 遮罩 + overlay（输出逐帧 bit-exact）

旧写法 `blend=all_expr='if(eq(mod(Y,2),0),if(lt(N,1.5),A,B),A)'` 要**逐像素**求值判行奇偶，
实测占单条编码耗时的绝大部分。改成「色块图带 alpha 行遮罩 + overlay」后：

| 指标（20s / 720×1276 片段，14 核 Mac） | 旧 blend | 新 overlay |
|---|---|---|
| 单条墙钟（编码到 /dev/null） | 6.24s（3.2x 实时） | **3.15s（6.4x 实时）** |
| 单条 CPU 时间 | 55.6s | **16.2s** |
| 4 条批量（workers=4） | 21.9s（并发几乎无收益） | **6.6s（1.9x 加速比）** |

两条滤镜链在同一素材上做过逐帧 `framemd5` 比对：**249/249 帧完全一致**（纯色图案与随机色块图案都验过）。
旧写法会让**单条编码就吃满十几个核**，所以「同时处理」开多大都没用；新写法才真正吃并发。
**别退回 blend 逐像素表达式**（回归测试里有断言守着）。

### 与样本的两处有意偏离（已定案，不要顺手改回来）

| 项 | 样本 22.mp4 / 同行新版 | 本工具 | 原因 |
|---|---|---|---|
| 封面保护帧数 | 前 5 帧整帧保留原画 | 只保护第 0 帧 | 用户 2026-09-19 定案：影响可忽略，不改 |
| 成品高度 | 跟随源片（源 1280 → 输出 1280，不裁） | 固定 1276 | 用户 2026-09-19 定案：素材分辨率统一，不改 |

## 六、编码配方（从样本码流反推，参数级 1:1）

x264 会把**本次编码的完整参数表**写进第一帧的 SEI（`user_data_unregistered`），
把码流里的这段 dump 出来就等于拿到了对方的命令行：

```
ref=3 deblock=1:1:0 analyse=0x3:0x113 me=hex subme=7 psy_rd=1.00,0.00 mixed_ref=0
me_range=16 trellis=0 8x8dct=1 chroma_qp_offset=-4 threads=4 lookahead_threads=4
sliced_threads=1 slices=4 interlaced=tff bframes=3 b_pyramid=2 weightb=1 open_gop=0
weightp=0 keyint=250 keyint_min=25 scenecut=40 rc_lookahead=10 rc=crf mbtree=1
crf=22.0 qcomp=0.60 aq=1:1.00
```

对应 `obfuscate.CLONE_X264`（31 项，逐字对齐）。ffmpeg 侧有 5 个非等价的写法，
每一项都踩过：

| 目标参数 | ffmpeg 写法 | 为什么 |
|---|---|---|
| `deblock=1:1:0` | `deblock=1\:0\:0` | ffmpeg 用 `:` 分隔 `-x264-params`，必须反斜杠转义 |
| `analyse=0x3:0x113` | `partitions=i4x4,i8x8,p8x8,b8x8` | 写 `analyse=all` 会多开 p4x4 |
| `chroma_qp_offset=-4` | `chroma-qp-offset=-2` | x264 在 `subme>=7` 时会自动再减 2 |
| `mbtree=1` | 必须显式写 | `preset superfast` 自带 `--no-mbtree` |
| `interlaced=tff` | `-flags +ilme+ildct -top 1`，且**放在 `-x264-params` 之前** | 顺序不对不生效 |

其它固定项：`-c:v libx264 -preset superfast -crf 22 -profile:v high -pix_fmt yuv420p`，
音频 `-c:a aac -b:a 192k -ar 44100 -ac 2`。CRF **不抖动**（固定 22）。

已知不可复现项：逐帧 SEI 的载荷字节（样本里 0x42 / 0x32 两种，本实现全是 0x32），
属 x264 core 164 与 165 的 `pic_struct` 取值差异；参数表零差异，不影响效果，不必纠结。

## 七、容器改写：把标准 MKV 改成样本形状

重编码产出的是一条**标准 MKV**，随后用纯 Python 逐字节重建（`_parse` / `_serialize` / `_write_size`），
改成样本的容器形状。人为破坏集中在五处：

| 位置 | 做法 | 效果 |
|---|---|---|
| `Tracks` → `Video` | `PixelWidth` / `PixelHeight` 各替换成**等长的 2 字节 `Void`**，并写 `DisplayUnit=4` | **唯一致命项**：解码器拿不到分辨率，整个文件被判无效 → 本地 `Invalid data found` |
| `Info` | `TimestampScale` 的位置换成 5 字节 `Void`；`MuxingApp` / `WritingApp` 的元素 ID 各 +1（写成 `0x4D81` / `0x5742`） | 时间基缺失 + 结构指纹异常 |
| `SeekHead` | 首位放 4 字节 `Void` 顶掉本应在那里的 CRC-32；第 2 条 `SeekID` 写成非法值 `0x84ECECEC` | 该索引条目失效 |
| `Tags` | 两条 Tag（UID 1 / 2）各挂一条 `DURATION`，值写死 `00:00:01.121000000` | 元数据不可信 |
| `Info.DateUTC` | 取**该条的处理时刻**（macOS 纪元：`(time.time() - 978307200)` 的纳秒） | 每份成品字节必然不同（见第九节） |

`Info.Duration` 写死 `1032.0`（毫秒），与样本一致。

实现上的三个关键约定：

1. **等长顶掉**：`Void` 与原字段字节数相同，文件结构不位移，后面所有元素的偏移原样可用。
   因此最小还原 = 把 `Void + Void + DisplayUnit` 换回 `PixelWidth + PixelHeight`。
2. **CRC-32 按 ffmpeg 的落盘约定写小端**：`struct.pack("<I", zlib.crc32(body))`。
3. **Segment size 固定写 8 字节**（样本如此；最短编码会写成 4~5 字节）。
   头部长度会变，所以 `SeekHead` 自身的长度要迭代求解（最多 10 轮收敛），
   求稳之后再把 `Cues` 的 `CueClusterPosition` 按同样的位移整体平移，保持索引自洽。

## 八、算法注册表（可扩展）

`obfuscate.py` 把「混淆算法」抽象成可切换的对象，`ALGORITHMS = {name: algo}`，`DEFAULT_ALGORITHM = "fieldmix"`。
**当前只有 `fieldmix` 一个。**

| 字段 | 类型 | 职责 |
|---|---|---|
| `name` | str | 算法唯一标识 |
| `label` | str | 展示名（界面用） |
| `encode_cmd(ffmpeg, src, mid, frames=None)` | callable | 返回重编码命令，先把源视频压成标准 MKV 中间件 |
| `rewrite(mid_bytes) -> bytes` | callable | 把中间件改写成该算法的混淆容器 |
| `needs_frames` | bool | 为真时调用方按「源帧数 − 1」截帧 |

加新算法 = 写一个 `_algo_xxx()` 返回上面这些字段 + 在 `ALGORITHMS` 里注册一行，**不动已有算法**。
命名约定：标识用 `YYMMDD`（如 `260919`），对应该算法**通过查重实测的当天**；一天只保留最终确认的那一个。

调用链：`ui/window.py` → `fission.process_one_output(..., algorithm=)` → `obfuscate.process_video(..., algorithm=)`，
`algorithm` 参数全程透传。

## 九、裂变随机化（每条字节必不同）

两个独立随机源，编码参数本身**不随机**（不抖 CRF、不写死假值 —— 那才是被查重的根因）：

1. **色块图种子**取 `time.time_ns()`，每条成品的图案都不同；
2. **容器 `DateUTC`** 取该条的处理时刻。

叠加「前贴 / 尾贴 / 封面每条独立随机抽取」，N 条成品哈希必然互不相同。

## 十、平台侧行为（实测，决定这招有没有用）

三个样本构成一条完整链路：`11.mp4`（原片）→ `22.mp4`（同行软件处理）→ `33.mp4`（快手对 22 的转码产物）。

| 观测 | 数据 | 结论 |
|---|---|---|
| 帧数 | 11: 931 → 22: 930 → 33: 930 | 丢的 1 帧发生在**同行软件**那一步；**平台一帧不丢** |
| 分辨率 | 11: 720×1276 → 22: 720×1276 → 33: 716×1276 | 平台重转码裁掉 4px 宽度 |
| 色块层 | 22 偶场 163.51 / 16.54 → 33 偶场 106.33 / 59.56 | **平台把色块场整层剥离**，画面回到接近原片的状态 |

推论（决定选素材）：

- 色块层只在**上传瞬间**骗过系统，一进转码管线就被撸掉；
- 判重最终看的是色块底下那层原画面 —— **原画面已进库的素材，怎么处理都过不了**；
- 有效手段排序：换全新素材 ≫ 加前贴/尾贴（几秒全新内容）> 色块层（上传瞬间错开）> 封面（只换 1 帧，很弱）；
- 前贴/尾贴本身也会被查重：同一片段复用率过高会直接命中，**候选池要攒够再批量发**。

## 十一、逆向新算法的方法（平台更新后怎么重做）

触发条件：平台改了查重/转码策略，现有产物又过不了。需要用户提供**① 原视频 ② 平台处理后的视频**两个样本。

1. **定位差异**：容器（ffprobe 能否读、有无异常元素）、编码（分辨率/帧率/core 版本/码率/GOP/SEI）、
   画面（逐帧逐场比对）、元数据（Duration / Tags / DateUTC 是否被写死）。
2. **逆推变换链**：把 ①→② 的每一步变化量化出来（裁几像素、码率多少、PSNR 多少），抽象成一条滤镜链。
3. **生成候选产物**：让产物比平台多一步「容器破坏逼它重转码」，编码参数则对齐样本 ② 的特征。
4. **验证闭环**：产出 N 份实测，确认过查重后把参数固化进 `obfuscate.py`，并按第八节登记新算法。

工具（都在项目根 `复刻22_已验证备份_20260919/`，长期存档，`/tmp` 会被清掉）：

| 工具 | 用途 |
|---|---|
| `容器还原_deobf.py <混淆产物> <输出.mkv> <W> <H>` | 把被改坏的容器还原成合法 MKV，好让 ffprobe / ffmpeg 能读 |
| `分析脚本/probe_container.py` | dump 容器元素结构（比对两边的破坏痕迹） |
| `分析脚本/sps.py` | 解析 SPS（分辨率、`frame_mbs_only`、场序、ref） |
| `分析脚本/fieldcheck.py`、`first_frames.py` | 逐场均值/标准差、前 N 帧的场结构 |
| `分析脚本/cmp_fields.py`、`cmp_frames.py` | 逐场像素对应关系、多时间点抽样比对 |

手法备忘：

- 抽帧**必须按时间戳对齐**（`-ss`），不能按帧号 —— 帧率不同的两个文件帧号不对应同一时刻。
- 找裁边量：对 dx/dy 穷举平移，MAD 最小的偏移即真实裁边量。
- 判断画面有没有被实质改动：产物与原片的 PSNR 应 > 35dB（内容基本没动）；< 30dB 说明方向错了。
- 混淆产物 ffprobe 拒读是**预期**，要看画面必须先还原容器。
- 性能类结论一律重复测量取中位数，单次计时会得出相反的方向。

## 十二、验证手法

```bash
# 回归检查（只用标准库 + 临时素材，不碰用户素材；需要 ffmpeg/ffprobe）
python3 video_frame_tool/tests/test_video_frame_tool.py
```

6 项用例：命名与随机抽取、拼接规格与时长、封面替换第 0 帧、复刻22 滤镜链与容器伪装值、
端到端一条成品（场结构 + 容器拒读 + 两份哈希不同）、`probe_media` / `_run` 的基础行为。

改动滤镜链或编码参数后必跑该脚本；端到端验证另需实测 N 份产物：**md5 全不同 + ffprobe 全部拒读**。
